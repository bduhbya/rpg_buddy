# Roadmap

## Working method

Implement one small phase at a time. Before coding, write its specification in `specs/<date_phase_name>/`, with scope, acceptance criteria, and a short human verification procedure. Detailed tasks and implementation choices belong in those phase specifications. Record completion evidence there before moving on.

The sequence below is the initial plan. Amend it explicitly as source review or implementation reveals new requirements.

Each phase delivers one coherent outcome with its own acceptance checks and may depend on completed earlier phases. It need not independently implement the complete user workflow. Keep implementation details in the phase specification and split a phase again if its acceptance checks reveal multiple substantial changes.

Use language-neutral fixtures and a small development harness to inspect domain and persistence behavior before their interface controls exist. Reuse the agreed independent input/output and invalid-data cases when introducing TypeScript tests, and retire overlapping Python calculation tracing as specified in `tech-stack.md`. The desktop shell provides an early runnable application; later phases add verified behavior incrementally.

Keep the domain, persistence, and UI responsibilities separate from their introduction onward. Defer concrete persistence APIs to the library and persistence phases, where their required behavior can be specified. Runtime definitions remain separate from specification documents and contract-verification fixtures.

## Feature-library follow-on commitment

Before implementing reusable feature selection, specify a bounded phase for system-specific feature definitions/catalog storage, exact version provenance, compatibility checks and copying selections into instance-owned entries. Templates retain generic modifierTargets and do not enumerate named features. Selected snapshots remain usable without a live library; upgrades require explicit user action. The current Phase 2 entry/effect contract is the snapshot baseline, not an implemented library. Schedule the follow-on explicitly when selecting the next scope; it is not implicitly added to the desktop shell, domain foundation, or sheet editing phases. Split the follow-on into separately verifiable catalog, selection, and upgrade phases if needed when specifying it.

## Phase 15 loading scope requirement

The definition loader must load and validate definitions only for the selected system and populate its in-memory catalog from that system's definitions. It must not eagerly read, parse, validate or retain definitions from the entire library. Lightweight system discovery for selection must remain separate from definition loading. Selecting a library alone must not trigger loading every system's definitions.

Carry this requirement into Phase 15 requirements, plan and validation. Verify with a multi-system library that selecting one system loads its definitions without reading other systems' definition payloads or populating the catalog with them. Include an unselected system with malformed definitions to prove that it neither blocks the selected system nor gets validated during that load. Phase 15 must specify catalog lifetime and release behavior when selection changes so previously selected systems do not accumulate in memory unintentionally. This requirement was requested on 2026-11-02; it does not change Phase 8's general-purpose catalog API.
